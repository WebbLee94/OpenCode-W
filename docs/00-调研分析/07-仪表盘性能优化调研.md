# 仪表盘性能优化调研

> 调研对象：Dashboard 6 个慢查询的根因分析与优化方案
> 调研时间：2026-07-08
> 数据来源：实测 perf trace（实际 OpenCode 数据库）、Schema 文档
> 关联文档：[03-数据库Schema参考](03-数据库Schema参考.md)、[04-Part数据模型调研](04-Part数据模型调研.md)、[01-首页仪表盘](../03-功能模块/01-首页仪表盘.md)

## 一、背景

Dashboard 首页需聚合展示 7 个数据卡片，共涉及 9 条 SQL 查询。实测数据显示存在明显性能两极分化：

| 查询 | 耗时 | 扫描表 |
|------|------|--------|
| `dashboard_session_trend` | **6-13ms** ✅ | session |
| `dashboard_message_trend` | **16-34ms** ✅ | message |
| `dashboard_overview` | **~90ms** ⚠️ | session |
| `dashboard_cost_trend` | **1,301-1,352ms** ❌ | part + session |
| `dashboard_tokens` (aggregate) | **1,462ms** ❌ | part |
| `dashboard_tokens` (grouped) | **1,470ms** ❌ | part |
| `dashboard_model_ranking` | **1,533-1,546ms** ❌ | part + session |
| `dashboard_skill_usage` | **1,537-1,560ms** ❌ | part |
| `dashboard_tool_ranking` | **1,542-1,570ms** ❌ | part |
| `dashboard_provider_stats` | **1,547-1,569ms** ❌ | part + session |

**仪表盘总加载时间约 8-9 秒**，其中 6 个慢查询占绝对主导（1.3-1.6s/个），用户体验不可接受。

---

## 二、根因分析

### 2.1 共性特征

6 个慢查询的耗时高度一致（1.3-1.6s），说明共享 **同一个性能瓶颈**。

所有慢查询的 WHERE 子句都包含 `json_extract(data, '$.type')` 表达式：

```sql
-- dashboard_tokens: 1,462ms
SELECT SUM(json_extract(p.data, '$.tokens.input')) AS input,
       SUM(json_extract(p.data, '$.tokens.output')) AS output,
       SUM(json_extract(p.data, '$.tokens.reasoning')) AS reasoning
FROM part p
WHERE json_extract(p.data, '$.type') = 'step-finish';

-- dashboard_tool_ranking: 1,570ms
SELECT json_extract(data, '$.tool') AS tool_name,
       COUNT(*) AS count
FROM part
WHERE json_extract(data, '$.type') = 'tool'
GROUP BY json_extract(data, '$.tool')
ORDER BY count DESC;

-- dashboard_model_ranking: 1,546ms
SELECT s.model,
       SUM(json_extract(p.data, '$.cost')) AS total_cost
FROM part p
JOIN session s ON s.id = p.session_id
WHERE json_extract(p.data, '$.type') = 'step-finish'
GROUP BY s.model
ORDER BY total_cost DESC;
```

### 2.2 为什么这么慢

**结论：缺少 `json_extract(data, '$.type')` 表达式索引，导致每次查询全表扫描 + 逐行 JSON 解析。**

查询执行过程：

| 步骤 | 操作 | 代价 |
|------|------|------|
| 1 | 遍历 `part` 表所有行 | 136,372 行（Schema 参考数据） |
| 2 | 对每行调用 `json_extract(data, '$.type')` | 解析 5-50KB JSON 文本 |
| 3 | 比对字符串是否等于 `'step-finish'` | 字符串比较 |
| 4 | 符合条件的行做聚合计算 | SUM/GROUP BY |

**全表扫描 → JSON 解析 → 过滤 → 聚合**，每一步都是线性放大。

### 2.3 为什么快查询快

```sql
-- dashboard_session_trend: 6ms
SELECT date(time_created / 1000, 'unixepoch') AS day,
       COUNT(*) AS count
FROM session
WHERE time_created BETWEEN ? AND ?
GROUP BY day
ORDER BY day;
```

`session` 表的 `time_created` 是独立列，SQLite 可直接利用 B-Tree 索引跳转到目标数据范围，无需全表扫描。同理 `message` 表也有 `time_created` 列上的索引。

### 2.4 关键数据量参考

| 表 | 行数 | 数据量 | 占DB |
|----|------|--------|------|
| **part** | **136,372** | **686 MB** | **81.2%** |
| message | 35,614 | 87 MB | 10.3% |
| session | 2,858 | — | — |

`part` 表不仅是最大的表，且 `data` 列存储未压缩的 JSON 文本（单行平均 5KB），全表扫描需要读取并解析数百 MB 的 JSON 数据。

## 三、已实施优化（Wave 1-3）

### 3.1 Wave 1 — 连接池（r2d2）

| 优化项 | 内容 |
|--------|------|
| 改动文件 | `Cargo.toml`、`db.rs` |
| 引入依赖 | `r2d2 0.8.10` + `r2d2_sqlite 0.25` |
| 结构变更 | `DbState` 从 `Mutex<Option<Connection>>` 改为 `Arc<Mutex<Option<Pool<SqliteConnectionManager>>>>` |
| 效果 | 并行查询不再竞争同一连接，避免查询间排队等待 |

### 3.2 Wave 2 — db.rs 重构

| 优化项 | 内容 |
|--------|------|
| 改动文件 | `db.rs` + 所有 command handler |
| 新接口 | `get_db()` 返回 `PooledConnection`（自动 deref 为 `Connection`） |
| 旧模式 | 两步获取：`let db = get_db(); let conn = db.lock().as_ref().unwrap();` |
| 新模式 | 一步获取：`let conn = get_db();` |
| 效果 | 编码更简洁，连接归还自动由 Pool 管理 |

### 3.3 Wave 3 — Session 查询优化

| 优化项 | 内容 |
|--------|------|
| 改动文件 | `commands/sessions.rs` |
| 提取 helper | `build_session_where()` 公共条件构建函数 |
| 子会话限流 | 子会话 batch 最多取 50 条，防止单会话展开数千条子会话 |
| 新增字段 | `sessions_detail` 查询增加 `msg_count` 和 `data_size` |

> **Wave 1-3 效果总结**：解决了连接竞争和代码质量问题，但 **慢查询的根因（json_extract 无索引）未触及**，Dashboard 加载时间改善有限。

## 四、待议优化方案（Wave 4）

### 4.1 核心思路 — 表达式索引

SQLite 3.9.0+（当前 SQLite 版本已支持）提供 **Expression Index**（表达式索引），可将 `json_extract(data, '$.type')` 的结果预先计算并存储在索引中：

```sql
-- 核心索引：覆盖 100% 的慢查询
CREATE INDEX IF NOT EXISTS idx_part_type 
    ON part(json_extract(data, '$.type'));

-- 组合索引：时间范围 + 类型过滤同时走索引
CREATE INDEX IF NOT EXISTS idx_part_type_time 
    ON part(json_extract(data, '$.type'), time_created);
```

**优化原理对比：**

| | 优化前 | 优化后 |
|---|---|---|
| 扫描方式 | 全表扫描，逐行 JSON 解析 | 索引查找，直接跳到匹配行 |
| 扫描行数 | 136,372 行全部扫描 | 仅扫描 `type='step-finish'` 的行 |
| JSON 解析 | 每行都解析 `data` 列 | 索引已预计算，零重复解析 |
| 时间复杂度 | O(N) × JSON 解析代价 | O(log N) + 少量行扫描 |

### 4.2 预期效果

基于数据量估算（假定 30% 的 part 为 `step-finish`）：

| 查询 | 优化前 | 预估优化后 | 提升倍数 |
|------|--------|-----------|---------|
| `dashboard_tokens` | 1,462ms | 30-100ms | **15-50x** |
| `dashboard_tool_ranking` | 1,570ms | 30-100ms | **15-50x** |
| `dashboard_skill_usage` | 1,560ms | 30-100ms | **15-50x** |
| `dashboard_model_ranking` | 1,546ms | 50-150ms | **10-30x** |
| `dashboard_provider_stats` | 1,569ms | 50-150ms | **10-30x** |
| `dashboard_cost_trend` | 1,352ms | 30-100ms | **10-45x** |

**仪表盘总加载预计从 ~9s 降至 ~0.5-1s。**

### 4.3 实施方案

```sql
-- db.rs 初始化连接池后执行：

PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;

-- ↓ 新增 3 条表达式索引 ↓
CREATE INDEX IF NOT EXISTS idx_part_type 
    ON part(json_extract(data, '$.type'));

CREATE INDEX IF NOT EXISTS idx_part_type_time 
    ON part(json_extract(data, '$.type'), time_created);

CREATE INDEX IF NOT EXISTS idx_part_time_created 
    ON part(time_created);
```

改动量：`db.rs` 增加约 10 行代码。`CREATE INDEX IF NOT EXISTS` 幂等安全，可重复执行。

### 4.4 风险与注意事项

| 风险项 | 说明 | 缓解措施 |
|--------|------|---------|
| 表达式索引增加写开销 | INSERT/UPDATE 时需同步更新索引 | 非频繁写操作，影响可忽略 |
| 索引占用磁盘空间 | `json_extract` 表达式计算结果 + B-Tree 结构 | 预计 <10MB，相比 686MB 的 part 数据可忽略 |
| **兼容性约束** | **修改 OpenCode 自有表结构** | **见第五节** |

## 五、决策约束

> ⚠️ **基本原则：不修改 OpenCode 自身的表结构和已有索引定义。**

OpenCode-W 作为第三方工具，其应用层建立在 OpenCode 的 SQLite 数据库之上。修改底层表结构（添加索引/列/触发器）在技术上行得通，但存在以下顾虑：

1. **维护耦合**：OpenCode 版本升级可能引入 schema 变更，与 OpenCode-W 添加的索引产生冲突
2. **职责边界**：OpenCode-W 的定位是"读取 + 展示"，将优化决策留给"写入方"（OpenCode 自身或用户手动维护）
3. **回滚复杂度**：添加索引不可逆（SQLite 删除索引需明确走 DROP，易遗漏）

### 技术替代方向（供后续决策参考）

若后续决定优化，可在以下方向进一步探索：

| 方向 | 说明 | 代价 |
|------|------|------|
| **复合索引 + 条件聚合** | 同 Wave 4 方案，仅在 `db.rs` 做 CREATE INDEX IF NOT EXISTS | 10 行代码，无侵入 |
| **聚合表/物化视图** | 定时将 part 数据摘要写入 OpenCode-W 自有的汇总表 | 需额外存储，首次构建慢 |
| **客户端缓存** | Dashboard 数据缓存 30s-5min，避免频繁触发慢查询 | 实现简单，但有数据延迟 |
| **虚拟列** | 需要在 OpenCode 源码侧给 part 表加 `type` 生成列 | 需 fork OpenCode，不可行 |

## 六、附录

### 6.1 慢查询 SQL 原文

#### dashboard_tokens

```sql
SELECT 
  COALESCE(SUM(json_extract(p.data, '$.tokens.input')), 0) AS input,
  COALESCE(SUM(json_extract(p.data, '$.tokens.output')), 0) AS output,
  COALESCE(SUM(json_extract(p.data, '$.tokens.reasoning')), 0) AS reasoning,
  COALESCE(SUM(json_extract(p.data, '$.tokens.cache_read')), 0) AS cache_read,
  COALESCE(SUM(json_extract(p.data, '$.tokens.cache_write')), 0) AS cache_write
FROM part p
WHERE json_extract(p.data, '$.type') = 'step-finish';
```

#### dashboard_model_ranking

```sql
SELECT 
  s.model,
  COALESCE(SUM(json_extract(p.data, '$.cost')), 0) AS total_cost,
  COALESCE(SUM(json_extract(p.data, '$.tokens.input')), 0) AS total_input,
  COALESCE(SUM(json_extract(p.data, '$.tokens.output')), 0) AS total_output,
  COALESCE(SUM(json_extract(p.data, '$.tokens.input') + 
           json_extract(p.data, '$.tokens.output')), 0) AS total_tokens,
  COUNT(*) AS count
FROM part p
JOIN session s ON s.id = p.session_id
WHERE json_extract(p.data, '$.type') = 'step-finish'
GROUP BY s.model
ORDER BY total_cost DESC;
```

#### dashboard_skill_usage

```sql
SELECT 
  json_extract(p.data, '$.agent') AS skill_name,
  COUNT(*) AS call_count,
  COALESCE(SUM(json_extract(p.data, '$.cost')), 0) AS total_cost
FROM part p
WHERE json_extract(p.data, '$.type') = 'step-finish'
  AND json_extract(p.data, '$.agent') IS NOT NULL
  AND json_extract(p.data, '$.agent') != ''
GROUP BY json_extract(p.data, '$.agent')
ORDER BY call_count DESC;
```

#### dashboard_tool_ranking

```sql
SELECT 
  json_extract(data, '$.tool') AS tool_name,
  json_extract(data, '$.tool_input') AS raw_input,
  COUNT(*) AS call_count,
  COALESCE(AVG(COALESCE(json_extract(data, '$.state.duration_ms'), 0)), 0) AS avg_duration
FROM part
WHERE json_extract(data, '$.type') = 'tool'
GROUP BY json_extract(data, '$.tool')
ORDER BY call_count DESC;
```

#### dashboard_provider_stats

```sql
SELECT 
  json_extract(p.data, '$.provider') AS provider,
  COUNT(*) AS call_count,
  COALESCE(SUM(json_extract(p.data, '$.cost')), 0) AS total_cost,
  COALESCE(AVG(json_extract(p.data, '$.latency_ms')), 0) AS avg_latency
FROM part p
JOIN session s ON s.id = p.session_id
WHERE json_extract(p.data, '$.type') = 'step-finish'
  AND json_extract(p.data, '$.provider') IS NOT NULL
GROUP BY json_extract(p.data, '$.provider')
ORDER BY total_cost DESC;
```

#### dashboard_cost_trend

```sql
SELECT 
  strftime('%Y-%m-%d', p.time_created / 1000, 'unixepoch') AS day,
  s.model,
  COALESCE(SUM(json_extract(p.data, '$.cost')), 0) AS cost
FROM part p
JOIN session s ON s.id = p.session_id
WHERE json_extract(p.data, '$.type') = 'step-finish'
  AND p.time_created >= ?
GROUP BY day, s.model
ORDER BY day;
```

### 6.2 已有的 part 表索引

| 索引名 | 列 | 是否覆盖慢查询 |
|--------|----|--------------|
| `part_message_id_id_idx` | `(message_id, id)` | ❌ — 仅用于按消息查片段 |
| `part_session_idx` | `(session_id)` | ❌ — 仅用于按会话查片段 |

两个现有索引均与 `json_extract(data, '$.type')` 的过滤条件**不匹配**，因此慢查询无法走索引。

### 6.3 实测方法

如需验证优化效果，可按以下步骤：

1. 在 `src-tauri/src/db.rs` 的 `open()` 函数中 `PRAGMA` 块后追加 3 条 `CREATE INDEX IF NOT EXISTS`
2. 执行 `cargo check` 确认编译通过
3. 运行 `cargo build --release && npm run tauri:dev`
4. 打开 Dashboard，观察加载耗时
5. 在 Rust 端打印每个 SQL 的查询时间（或使用 SQLite `.timer` / `EXPLAIN QUERY PLAN`）
