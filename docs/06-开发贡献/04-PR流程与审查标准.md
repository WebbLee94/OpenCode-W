# PR 流程与审查标准

## 一、PR 提交前自查

提交 PR 前必须完成：

- [ ] `npx tsc --noEmit` 无错误
- [ ] `npm run lint` 无错误
- [ ] `npm run test` 通过
- [ ] 相关文档已更新（遵循 [文档同步约定](../../AGENTS.md)）
- [ ] 提交信息遵循 Conventional Commits（中文、动词开头、单行）
- [ ] CHANGELOG.md 已更新（如涉及用户可见变更）

## 二、PR 模板

参考 `.github/PULL_REQUEST_TEMPLATE.md`，关键段落：

### 2.1 变更说明
- 这个 PR 做了什么？
- 为什么需要这个变更？

### 2.2 变更类型
- [ ] feat 新功能
- [ ] fix Bug 修复
- [ ] refactor 重构
- [ ] docs 文档
- [ ] chore 构建/工具

### 2.3 测试
- [ ] 单元测试已添加/更新
- [ ] 手动测试已通过
- [ ] E2E 测试已添加（如涉及关键流程）

### 2.4 关联 Issue
- Closes #xxx

## 三、CI 要求

PR 必须通过 CI 4 平台构建：

| 平台 | 架构 | 关键检查项 |
|------|------|-----------|
| macOS | arm64 + x64 | 构建成功、Universal 包正确 |
| Windows | x64 + arm64 | 构建成功、NSIS 安装包正确 |
| Linux | x64 | 构建成功、AppImage 可执行 |

CI 失败处理：
- 优先修复 CI 错误
- 平台特定问题需在 PR 描述中说明

## 四、Review 清单

### 4.1 代码审查
- [ ] 命名清晰、符合规范
- [ ] 无硬编码值（使用常量/配置）
- [ ] 错误处理完整
- [ ] 无副作用（遵循不可变性）
- [ ] 无安全漏洞（SQL 注入、路径遍历、XSS）

### 4.2 架构审查
- [ ] 遵循进程边界（主进程/渲染进程）
- [ ] 不引入禁止依赖（ORM/Redux/ECharts）
- [ ] DTO 类型定义在 shared/
- [ ] IPC 通道在白名单中

### 4.3 文档审查
- [ ] 新功能有对应文档（03-功能模块/ 或 04-技术方案/）
- [ ] 重大决策有 ADR（05-决策记录/）
- [ ] README/AGENTS.md 同步更新（如涉及）

## 五、合并流程

1. 至少 1 名维护者 Review 通过
2. CI 4 平台构建通过
3. Squash and Merge（保持提交历史整洁）
4. 删除分支
5. 如涉及版本发布，按 [02-版本发布清单.md](../01-交付定义/02-版本发布清单.md) 执行

## 六、分支策略

| 分支 | 用途 | 保护 |
|------|------|------|
| master | 主分支 | 必须通过 PR 合并 |
| release | 发布分支 | 必须通过 PR 合并 |
| feature/* | 功能分支 | 无 |
| fix/* | 修复分支 | 无 |
